# Spaces Feature: Production Implementation Plan

## Status and scope

This document is the normative implementation design for KeptIt's private Spaces feature. The
feature is implemented by Alembic revision `20260805_0005`, the owner-scoped Spaces API/service
layer, and the responsive library Spaces interface.

A Space is a named, user-owned organizational container. A Discovery may be assigned to zero, one,
or many Spaces, and a Space may contain zero or many Discoveries. Spaces are private and have
exactly one owner. This feature does not change authentication, the Discovery schema, or existing
Discovery behavior. It does not introduce Tags, AI, sharing, collaboration, or browser extensions.

The plan assumes the existing session authentication, CSRF/trusted-origin protection, error
envelope, UUID generation convention, and Discovery ownership boundary remain authoritative.

## Product and domain rules

- A user may create, list, view, rename, describe, and permanently delete only their own Spaces.
- A Discovery may be assigned only to a Space owned by the same user.
- An unassigned Discovery and an empty Space are both valid.
- Membership does not transfer or duplicate ownership. It is organization metadata only.
- Membership applies equally to active and archived Discoveries. Archiving does not remove it.
- There is no default Space and no implicit Space creation.
- Space names are unique per user after normalization. Different users may use the same name.
- A Discovery may occur at most once in a given Space. Repeating the assignment is idempotent.
- Spaces are not shareable, collaborative, public, nested, or ordered in this release.

## Database schema

All identifiers are PostgreSQL `uuid`; application-generated UUIDv4 remains acceptable under the
current project convention, with UUIDv7 preferred only after runtime support is deliberately
adopted. All timestamps are `timestamptz`, written in UTC. Alembic owns every schema change.

### `spaces`

| Column | Type | Null/default | Rules |
| --- | --- | --- | --- |
| `id` | `uuid` | not null | Primary key; generated by the application |
| `user_id` | `uuid` | not null | Owning user; immutable |
| `name` | `varchar(100)` | not null | Trimmed display value; 1–100 Unicode code points |
| `normalized_name` | `varchar(200)` | not null | Application-derived uniqueness key; never returned |
| `description` | `varchar(500)` | null | Trimmed plain text; empty input becomes null |
| `created_at` | `timestamptz` | not null; current transaction time | Immutable creation time |
| `updated_at` | `timestamptz` | not null; current transaction time | Changes only when Space fields change |

Constraints and indexes:

- `pk_spaces` primary key on `id`.
- `fk_spaces_user_id_users` from `user_id` to `users.id ON DELETE CASCADE`.
- `uq_spaces_user_id_normalized_name` unique on `(user_id, normalized_name)`; this is the
  concurrency-safe duplicate-name authority.
- `uq_spaces_user_id_id` unique on `(user_id, id)` to support tenant-aware composite foreign keys.
- `ck_spaces_name_nonempty` requires `char_length(name) > 0`.
- `ck_spaces_normalized_name_nonempty` requires `char_length(normalized_name) > 0`.
- `ck_spaces_description_length` requires null or `char_length(description) <= 500`.
- `ix_spaces_user_updated_id` on `(user_id, updated_at DESC, id DESC)` supports stable owner-scoped
  keyset pagination. The unique owner/name index supports name lookup and sorting; do not add a
  redundant single-column `user_id` index.

`normalized_name` is computed at the application boundary from the trimmed name using Unicode NFKC
normalization followed by Unicode case folding. The normalization algorithm is a versioned domain
contract and must have shared backend fixtures. It does not collapse internal whitespace or remove
punctuation. Its wider column allows case folding to expand text. The display `name` preserves the
user's accepted spelling and casing. Database checks are defense in depth; application validation
is authoritative for Unicode code-point limits.

### `space_memberships`

| Column | Type | Null/default | Rules |
| --- | --- | --- | --- |
| `id` | `uuid` | not null | Primary key; generated by the application |
| `user_id` | `uuid` | not null | Immutable tenant key inherited from both parents |
| `space_id` | `uuid` | not null | Owned Space |
| `discovery_id` | `uuid` | not null | Owned Discovery |
| `created_at` | `timestamptz` | not null; current transaction time | Assignment time |

Constraints and indexes:

- `pk_space_memberships` primary key on `id`.
- `fk_space_memberships_user_id_users` from `user_id` to `users.id ON DELETE CASCADE`.
- `fk_space_memberships_user_space` from `(user_id, space_id)` to
  `spaces(user_id, id) ON DELETE CASCADE`.
- `fk_space_memberships_discovery_id_discoveries` from `discovery_id` to
  `discoveries.id ON DELETE CASCADE`.
- A `BEFORE INSERT OR UPDATE OF user_id, discovery_id` ownership trigger verifies that the
  referenced Discovery's existing `user_id` equals `NEW.user_id`; otherwise it raises a stable
  integrity failure. Discovery ownership is immutable, so no Discovery-side trigger is required.
  This provides defense in depth without changing the Discovery schema.
- `uq_space_memberships_space_id_discovery_id` unique on `(space_id, discovery_id)` so concurrent
  duplicate assignments cannot create duplicate rows.
- `ix_space_memberships_user_space_created_id` on
  `(user_id, space_id, created_at DESC, id DESC)` for paginated Space contents and FK support.
- `ix_space_memberships_user_discovery_space` on `(user_id, discovery_id, space_id)` for displaying
  and removing a Discovery's assignments and for FK support.

The composite Space foreign key and Discovery-owner trigger make a cross-user membership
structurally impossible even if a service bug bypasses authorization. The explicit `user_id` is
intentional tenant denormalization for enforcement and efficient owner-led queries. All three
ownership values are supplied from already owner-scoped parent queries in one transaction; clients
never supply `user_id`.

## Ownership and authorization

Authentication establishes the caller; Space authorization remains a separate service concern.
Every Space and membership read or mutation starts with `current_user.id` and uses owner predicates
in the SQL query. A UUID by itself grants no access.

- Fetch a Space by `(spaces.user_id, spaces.id)`, never by `id` followed by an ownership check.
- Fetch a Discovery for assignment by `(discoveries.user_id, discoveries.id)` in the same
  transaction as the membership write.
- The database ownership constraints are defense in depth, not a replacement for scoped queries.
- For an absent or foreign Space or Discovery, return the same `404 resource_not_found` response.
  Do not reveal which resource exists, its owner, name, or membership count.
- Collection results and counts are owner-scoped before filtering, joining, ordering, or pagination.
- There are no administrator, sharing, invitation, role, or collaborator exceptions.

## Duplicate and concurrency rules

### Space names

Names conflict only within one user's account after the defined normalization. Creation or rename
to an existing normalized name returns `409 space_name_conflict` with a safe field error on `name`.
The response may include the conflicting Space's ID because it belongs to the authenticated user;
it must not include private content beyond what is needed to resolve the conflict.

The service may pre-check for a useful response, but must catch the named unique-constraint failure
because that constraint resolves concurrent requests. It must not parse database error strings.
A rename that changes only display casing is allowed when the existing normalized key belongs to
that same Space.

### Memberships

`PUT` assignment is idempotent. If the exact membership already exists, it returns the existing
representation and does not alter `created_at`. Concurrent first assignments converge on one row;
the service handles the named unique constraint and reads the owned existing row. Membership IDs
are opaque implementation identifiers and are returned for representation consistency, but client
operations address the parent pair.

## Rename behavior

`PATCH` accepts at least one mutable field and uses partial-update semantics. Renaming changes
`name`, `normalized_name`, and `updated_at` atomically; it never changes the Space ID, owner,
memberships, Discovery records, or membership timestamps. Sending values equal to stored values is
a successful no-op and does not advance `updated_at`. A normalized-name conflict rolls the entire
request back. Clients should keep the edit form open, preserve input, and focus the name field on a
conflict.

## Delete behavior

Space deletion is immediate and permanent in the live database. The API requires an explicit
confirmation interaction in the UI, then deletes the owner-scoped Space in one transaction.
`ON DELETE CASCADE` removes only its `space_memberships`; it never deletes, archives, or modifies a
Discovery. Deleting a Discovery through its existing behavior cascades that Discovery's membership
rows. Deleting a user through the existing account lifecycle cascades Spaces and memberships.

A successful delete returns `204`. Repeating it, using a malformed valid UUID that does not exist,
or targeting another user's Space returns the same `404`. The UI must state that the Space will be
removed but its Discoveries will remain. There is no Space archive, trash, or undo in this release.
Encrypted backups expire under the platform's documented retention schedule rather than being
selectively rewritten.

## API contract

All routes are under `/api/v1`, require the existing authenticated session, and use the existing
trusted-origin/CSRF policy for mutations. Responses use explicit schemas and the existing error
envelope. Unknown JSON fields are rejected. Dates are RFC 3339 UTC instants.

### Space endpoints

| Method and path | Purpose | Success | Important errors |
| --- | --- | --- | --- |
| `POST /spaces` | Create an empty Space | `201` Space; `Location` header | `422`, `409` |
| `GET /spaces` | List caller's Spaces | `200` paginated collection | `422` cursor/limit |
| `GET /spaces/{space_id}` | Read one owned Space | `200` Space | `404` |
| `PATCH /spaces/{space_id}` | Rename and/or edit description | `200` Space | `404`, `409`, `422` |
| `DELETE /spaces/{space_id}` | Permanently delete Space | `204` | `404` |

Create body: `{ "name": string, "description"?: string | null }`. Patch body uses the same mutable
fields, both optional, but must contain at least one. `null` is invalid for `name` and clears
`description`. The Space representation contains `id`, `name`, `description`, `discovery_count`,
`created_at`, and `updated_at`; it never exposes `user_id` or `normalized_name`.

`GET /spaces` accepts `limit` (default 50, minimum 1, maximum 100), optional opaque `cursor`, and
`sort=updated_desc|name_asc` (default `updated_desc`). It returns `items` and `next_cursor`.
`discovery_count` includes active and archived Discoveries because membership is independent of
archive state. Counts must be computed in one owner-scoped aggregate query, not per-row queries.
Cursors encode the effective sort keys and are validated as opaque signed or integrity-protected
values; clients do not construct them.

### Membership endpoints

| Method and path | Purpose | Success | Important errors |
| --- | --- | --- | --- |
| `PUT /spaces/{space_id}/discoveries/{discovery_id}` | Idempotently assign an owned Discovery | `200` existing or `201` created | `404`, `422` |
| `DELETE /spaces/{space_id}/discoveries/{discovery_id}` | Remove an assignment | `204` | `404` |
| `GET /spaces/{space_id}/discoveries` | List assigned Discoveries | `200` paginated collection | `404`, `422` |

The `PUT` body is empty. Its representation contains `id`, `space_id`, `discovery_id`, and
`created_at`, never `user_id`. Membership deletion returns `404` when the owned pair is not assigned
and uses the same response for foreign resources. The list endpoint accepts `limit` (1–100), opaque
`cursor`, and `archive=active|archived|all` (default `active`), and uses stable membership order
`(created_at DESC, id DESC)`. It returns the existing public Discovery representation without
adding or changing Discovery fields.

No bulk replacement endpoint is included initially: set replacement has ambiguous lost-update
semantics and larger authorization/transaction limits. The client uses bounded individual
idempotent operations and refetches authoritative state after completion. A future batch endpoint
requires an item cap, atomic all-or-nothing validation, idempotency semantics, and a concurrency
contract.

## Validation rules

- Path IDs must parse as UUIDs. Invalid syntax returns `422`; unknown and foreign valid IDs return
  `404`.
- `name` must be a string, trimmed of leading/trailing Unicode whitespace, and contain 1–100 Unicode
  code points after trimming. Control characters (Unicode category `Cc`, except none are needed) and
  null bytes are rejected. HTML is stored as text and escaped on output.
- `normalized_name` is server-computed and cannot appear in input.
- `description` must be null or a string of at most 500 Unicode code points after trimming. Empty or
  whitespace-only becomes null. Control characters and null bytes are rejected.
- Request bodies have conservative byte-size limits at the HTTP boundary in addition to field
  limits. Content type must be JSON for body-bearing endpoints.
- List limits, enums, and cursors are allowlisted and bounded. Invalid or stale cursors return a
  safe validation error rather than falling back to the first page.
- Membership requests accept no user-controlled ownership or timestamp fields. Both parents must
  exist under the current owner; archived Discoveries remain valid assignment targets.
- Validation failures use field-specific, stable machine-readable details and never echo unsafe
  content into logs or HTML.

## UX flows

### Create a Space

1. From a Spaces index or Discovery organization control, the user chooses **New Space**.
2. A labelled dialog requests a name and optional description, shows length guidance, and performs
   immediate client validation while the server remains authoritative.
3. Submission disables duplicate sends and exposes an accessible busy state.
4. On success, the new empty Space appears and focus moves to its heading or returns to the invoking
   assignment control. On a name conflict, input is retained and focus moves to the name error.

Creating a Space from a Discovery does not silently assign it: after successful creation, the UI
explicitly selects and assigns it, and independently reports any assignment failure.

### Browse a Space

The Spaces index supports loading, empty, error, and paginated states. Each item shows its name,
optional description, and Discovery count. A Space detail view shows its paginated active
Discoveries by default, with an explicit archived/all filter. An empty Space explains how to assign
Discoveries without suggesting that the content was deleted.

### Assign and remove Discoveries

From a Discovery card/detail or a Space detail view, an accessible multi-select/checklist shows only
the caller's Spaces. Selecting a Space performs or queues an idempotent assignment; deselecting it
removes the assignment. The UI uses optimistic state only if it can roll back and announce a failed
request, then refetches authoritative memberships after a multi-action sequence. A Discovery may
show zero or many selected Spaces. Archived Discoveries retain their selections.

### Rename or edit

The owner opens Space settings, edits the name and/or description, and saves. On success, every
visible occurrence updates without changing navigation identity. Validation or conflict errors
preserve the form. Concurrent changes resolve last-write-wins in this release; a later conditional
request contract may use `updated_at`/ETag if real multi-device overwrite problems are observed.

### Delete

The owner chooses **Delete Space**, sees the exact Space name and a clear statement that Discoveries
will remain, and confirms the destructive action. After `204`, the UI removes the Space, clears any
active Space filter, and navigates to the Spaces index. Failure leaves the view intact with a safe,
retryable message. Keyboard focus, visible focus, labels, live announcements, and reduced-motion
preferences apply throughout; target WCAG 2.2 AA.

## Security and privacy considerations

- Owner predicates on every query plus database tenant constraints prevent IDOR and cross-tenant
  membership, including under service defects.
- Foreign and missing IDs are indistinguishable. Logs use route templates, request IDs, safe error
  codes, and authenticated actor IDs where policy permits; they exclude names, descriptions, UUIDs
  from raw paths, and request bodies.
- Existing secure cookie authentication, HTTPS, narrow CORS, CSRF/trusted-origin checks, parameterized
  SQLAlchemy statements, and output escaping apply unchanged.
- Apply per-user and IP-aware rate limits to create, rename, delete, and membership mutations before
  production. Bound pagination and request sizes to resist resource exhaustion.
- Avoid leaking cross-user data through counts, uniqueness errors, timing-dependent prechecks,
  autocomplete, cache keys, metrics labels, or error details. Private responses use an appropriate
  no-store cache policy.
- Database credentials retain least privilege; production backups are encrypted, access-controlled,
  restore-tested, and expired on schedule.
- Space names and descriptions are private user-authored content. They are excluded from telemetry,
  audit detail, exception reports, and analytics.

## Migration and rollout strategy

Use one focused, reviewed Alembic revision after the currently deployed head:

1. Preflight production migration state, PostgreSQL version, existing constraint names, and UUID
   generation convention. Confirm no legacy `spaces` or `space_memberships` tables exist.
2. Create `spaces`, its named constraints, and indexes.
3. Create `space_memberships`, foreign keys, uniqueness rule, ownership trigger, and
   indexes. Do not alter the `discoveries` table.
4. Run migration upgrade/downgrade tests against PostgreSQL and inspect generated SQL. The downgrade
   drops memberships before Spaces and removes only the supporting Discovery constraint created by
   this revision.
5. Deploy the backward-compatible migration before application instances that use the tables. Do
   not serve or advertise the feature until migration success is verified.
6. Deploy backend endpoints behind a disabled feature flag, run authenticated ownership and cascade
   smoke tests, then deploy the frontend and enable gradually. Roll back application code by
   disabling the flag; retain additive tables during incident rollback unless a separately reviewed
   downgrade is safe and no user data has been written.
7. Monitor latency, 4xx/5xx rates, unique-conflict rates, database locks, query plans, and index use
   without recording private names or descriptions.

There is no data backfill and no production seed. Existing Discoveries begin unassigned. If an
unexpected legacy table exists, stop and write a dedicated audited data migration with collision
and ownership reports; never infer ownership or discard rows automatically. On a large production
table, stop the rollout and resolve it through a separately reviewed migration.

## Test strategy

### Schema and migration tests

- Upgrade from current head, validate every column/type/default/named constraint/index, downgrade,
  and upgrade again on PostgreSQL.
- Prove user deletion cascades Spaces/memberships, Space deletion preserves Discoveries, Discovery
  deletion removes memberships, and archive/restore leaves memberships unchanged.
- Attempt direct cross-owner membership insertion and assert the database ownership constraint
  rejects it.
- Assert duplicate normalized names and duplicate membership pairs fail under concurrent inserts.

### Backend unit and service tests

- Cover name/description trimming, Unicode NFKC/case-fold normalization, expansion edge cases,
  limits, control characters, null/empty behavior, and stable error mapping.
- Cover create, no-op and casing-only rename, conflict rename rollback, description clearing,
  owner-scoped list/count/order/cursors, and transactional timestamps.
- Cover membership create/idempotency/remove, active and archived Discoveries, parent deletion, and
  concurrent assignment.

### API and authorization tests

- Require authentication on every route and trusted-origin/CSRF checks on every mutation.
- For each get/list/create/patch/delete/assignment path, test own resources, another user's Space,
  another user's Discovery, mixed-owner parents, random UUIDs, and malformed UUIDs.
- Assert foreign and missing resources have identical status/code/body shape and expose no names,
  counts, membership state, or ownership.
- Test request-size, content-type, unknown-field, field-length, pagination-limit, enum, and cursor
  failures; verify the stable error envelope.
- Test no N+1 count/list behavior and use representative `EXPLAIN (ANALYZE, BUFFERS)` fixtures for
  owner listing, Space contents, and Discovery membership lookup.

### Frontend and end-to-end tests

- Component-test create/edit/delete forms, conflict and validation focus, loading/empty/error states,
  membership selection rollback, pagination, archive filter, and destructive copy.
- Test keyboard-only operation, visible focus, accessible names/descriptions, announcements, dialog
  focus trapping/restoration, and representative mobile/desktop layouts.
- End-to-end test create → assign one Discovery to multiple Spaces → browse → rename → remove one
  assignment → delete Space, proving Discoveries remain and another user's Space is inaccessible.

### Operational verification before release

Run the repository's documented backend and frontend test, format, lint, type-check, build, and
migration commands. Add a production-like PostgreSQL concurrency suite, migration smoke test,
authorization regression suite, and backup/restore exercise. The implementation completion report
must list exact commands and outcomes; the feature is not complete while an applicable check fails.

## Future scalability considerations

- UUIDv7 can improve index locality for newly created rows once adopted project-wide; mixed UUID
  versions require no schema change. Do not rewrite existing IDs.
- Keyset pagination and owner-leading indexes avoid offset degradation. Validate query plans at
  realistic skew, including users with many Spaces and large Space memberships.
- Count aggregation is computed on read initially. If measured latency requires caching, add an
  asynchronously repairable or transactionally maintained counter with drift detection; do not add
  one preemptively.
- Individual membership calls are adequate initially. A future bulk API should be bounded,
  transactional, idempotent, and explicit about lost-update behavior.
- Partitioning, RLS, read replicas, and sharding are not initial requirements. RLS is a worthwhile
  defense-in-depth evaluation before higher scale or more access paths. If sharding becomes
  necessary, `user_id` is the routing key already present on both tables.
- Space ordering, nesting, archival, icons, and search require separate product evidence and schema
  decisions. Sharing or collaboration would fundamentally change authorization and is explicitly
  outside this design; it must not reuse `space_memberships`, whose rows mean Discovery assignment.
- Cache entries, background work, search documents, and future derived data must carry `user_id`,
  use owner-separated keys, and be invalidated on rename, membership change, Space deletion, and
  account purge.

## Implementation sequence and completion gates

1. Add the Alembic schema revision and PostgreSQL migration tests.
2. Add persistence models and typed validation/response schemas without changing authentication or
   Discovery models/contracts.
3. Add owner-scoped Space and membership services with constraint-aware conflict handling.
4. Add versioned routes and authorization/API tests.
5. Add the Spaces index/detail/settings and membership UI with accessibility tests.
6. Add end-to-end, performance/query-plan, security, migration, and operational tests.
7. Roll out behind a feature flag using the migration-first sequence above, observe, then enable.

Completion requires all ownership, cascade, duplicate, validation, accessibility, concurrency, and
migration cases above to pass; reviewed query plans at representative data size; privacy-safe
monitoring; and updated public product documentation. No part of this plan authorizes changes to
authentication or Discovery behavior, or the introduction of excluded features.
