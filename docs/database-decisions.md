# Database Decisions

These decisions guide the conceptual model and future Alembic migrations. “Final” means a strong default that should change only with new evidence; “revisitable” identifies an intentional extension point.

## ADR-001 — Primary keys

- **Context:** IDs cross API boundaries, must not reveal row counts, and may eventually be created by more than one process.
- **Decision:** Use PostgreSQL `uuid` primary keys generated by the application. Prefer time-ordered UUIDv7 when the selected runtime/library supports it reliably; UUIDv4 is an acceptable initial implementation and does not require a migration to UUIDv7 for existing rows. Join tables use either a UUID primary key or their two foreign keys as explicitly decided per feature; Space Membership uses a UUID primary key.
- **Alternatives considered:** Identity `bigint` keys are compact and index-friendly but enumerable; dual internal integer/public UUID keys add complexity without current benefit.
- **Consequences:** Larger indexes than integers and random UUIDv4 insertion cost; stable non-enumerable public identifiers and simpler distributed creation.
- **Status:** Final on UUID; revisitable on v4 versus v7 before the first model migration.

## ADR-002 — Ownership and tenant isolation

- **Context:** Every library is private and authorization failures are high impact.
- **Decision:** Put non-null `user_id` ownership on every top-level private resource. Scope every repository query and mutation by the authenticated user. Join-table writes must verify that both parents share the same owner. Use composite owner-aware database constraints later if risk or team size justifies denormalized owner keys; PostgreSQL row-level security is defense-in-depth to evaluate, not the initial authorization mechanism.
- **Alternatives considered:** Relying on opaque IDs, UI controls, or service checks after an unscoped fetch; shared global resources; immediate RLS.
- **Consequences:** Some repetitive predicates and authorization tests, but visible ownership boundaries and non-enumerating access behavior.
- **Status:** Final; RLS is revisitable.

## ADR-003 — Soft deletion and permanent deletion

- **Context:** Users need recovery from ordinary decluttering but must also be able to remove private data.
- **Decision:** Do not apply a universal `deleted_at`. Use archive for reversible hiding. An explicit delete permanently removes a Discovery and cascades its dependent data in the live database. Account deletion may use a short, documented pending-deletion window before purge. Backups expire on a disclosed schedule and are not selectively mutated.
- **Alternatives considered:** Soft-delete every table; immediate irreversible account purge; indefinite tombstones.
- **Consequences:** Simpler uniqueness and queries, honest delete semantics, and no in-app restore after permanent deletion. Recovery exists only through archive or a declared account grace period.
- **Status:** Final for Discoveries; account grace period is revisitable before launch.

## ADR-004 — Archive versus delete

- **Context:** “No longer in my active library” and “erase this data” are different intentions.
- **Decision:** `discoveries.archived_at` represents reversible archive state; null means active. Delete is a separate explicit, destructive operation. Archived Discoveries still participate in duplicate detection.
- **Alternatives considered:** Boolean `is_archived`; treating archive as soft delete; allowing a second active copy of an archived URL.
- **Consequences:** Timestamp records when archiving occurred and supports eligibility rules; queries must deliberately select active/all views.
- **Status:** Final.

## ADR-005 — Canonical URLs and duplicate detection

- **Context:** Equivalent share/tracking URLs should not silently create duplicates, while aggressive normalization can merge distinct pages.
- **Decision:** Preserve `original_url`. Store a conservative, application-derived `canonical_url`, a fixed-size `canonical_url_hash`, and `normalization_version`. Do not synchronously follow redirects to establish identity. A unique `(user_id, canonical_url_hash)` constraint is authoritative; the service compares canonical strings to guard against the extremely unlikely hash collision and reports a safe conflict.
- **Alternatives considered:** Unique full URLs, provider IDs alone, redirect resolution, fuzzy matching, PostgreSQL `text` uniqueness without a hash.
- **Consequences:** Fast bounded duplicate index and reproducible behavior. Normalization changes require a reviewed backfill/collision plan; a hash collision cannot be resolved by a second insert under the initial constraint and must fail safely.
- **Status:** Final on preserved original/versioned canonical forms; normalization rules are revisitable and versioned.

## ADR-006 — Duplicate scope

- **Context:** Different users may independently discover the same source, with different private context.
- **Decision:** Enforce uniqueness per user, including archived Discoveries, never globally. Do not create a shared global URL row in the MVP.
- **Alternatives considered:** Global URL uniqueness with user-save joins; active-only uniqueness; allowing arbitrary duplicates.
- **Consequences:** Strong privacy isolation and simple deletion; fetched metadata may be duplicated across users until a carefully privacy-reviewed cache is justified.
- **Status:** Final for MVP; shared metadata caching is revisitable.

## ADR-007 — Discoveries and Spaces

- **Context:** One Discovery may serve several projects or themes, and one Space contains many Discoveries.
- **Decision:** Model a many-to-many relation through `space_memberships`. Each membership has a UUID primary key and an immutable tenant `user_id`; unique `(space_id, discovery_id)` preserves pair identity. A composite tenant-aware Space foreign key and a Discovery-owner trigger enforce same-owner assignment in PostgreSQL without modifying the Discovery schema. See [Spaces feature implementation plan](spaces-implementation-plan.md).
- **Alternatives considered:** One `space_id` on Discovery; an array of IDs; a generic polymorphic membership table.
- **Consequences:** Flexible organization and database-enforced tenant integrity at the cost of a join, a denormalized tenant key, and a narrowly scoped ownership trigger. Deleting a Space removes only memberships.
- **Status:** Final.

## ADR-008 — Tags versus Spaces

- **Context:** Both organize Discoveries but communicate different user intent.
- **Decision:** Spaces are named, navigable collections; Tags are lightweight cross-cutting labels. Keep separate tables and interfaces. Both are user-owned and many-to-many with Discoveries.
- **Alternatives considered:** A single taxonomy table with type; hierarchical universal labels; free-form arrays.
- **Consequences:** Clear product language and independent evolution, with some similar persistence code.
- **Status:** Final; hierarchy for either concept is future and requires evidence.

## ADR-009 — Intent representation

- **Context:** KeptIt should remember why a Discovery was saved and what the user intends to do, but the vocabulary is not validated.
- **Decision:** MVP stores optional free-form `save_reason` text on Discovery. Do not introduce a database enum or intent table initially. Add `discovery_intents` later if product research demonstrates multiple intents, lifecycle, or filtering; use application-validated text/check constraints rather than a PostgreSQL enum for an evolving vocabulary.
- **Alternatives considered:** PostgreSQL enum column; fixed lookup table; full intent entity immediately.
- **Consequences:** Low-friction capture and no premature taxonomy, but weak structured filtering in MVP.
- **Status:** Revisitable after usage research.

## ADR-010 — Source metadata separation

- **Context:** User-authored context must never be confused with or overwritten by fetched facts.
- **Decision:** Discovery stores ownership, URLs, deterministic platform, and personal context. `metadata_records` later stores externally fetched title, description, thumbnail, creator/publisher, publication time, provider, and fetch provenance. MVP custom title is explicitly user-authored. Do not add the metadata table until enrichment begins.
- **Alternatives considered:** All fields on Discovery; immutable snapshot per fetch from day one; external document store.
- **Consequences:** Clear provenance and independent refresh/deletion. Reads may require a join. Snapshot history can be added later if a real need emerges.
- **Status:** Final on separation; current-record versus snapshot history is revisitable.

## ADR-011 — Visits and revisit counters

- **Context:** Memory features may use revisit history, but detailed behavioral telemetry is sensitive and can grow quickly.
- **Decision:** Add append-only `discovery_visits` only when a user-facing history or rediscovery feature needs it. Record minimal event type, surface, and time. Compute counts from events initially; add cached `visit_count`/`last_visited_at` only after profiling, updated transactionally or by an idempotent projection.
- **Alternatives considered:** Counter columns only; analytics platform events; tracking every outbound browser navigation.
- **Consequences:** Auditable event semantics and future flexibility, balanced by retention and aggregation costs. No behavioral tracking is included in MVP.
- **Status:** Revisitable when the feature is designed.

## ADR-012 — Future embeddings

- **Context:** Semantic retrieval may require vectors, but models, dimensions, chunking, and consent can change.
- **Decision:** Keep embeddings in PostgreSQL with the `pgvector` extension when semantic search is implemented. Use a separate versioned table keyed to its owner and source/chunk, recording model, dimensions, content fingerprint, created time, and vector. Apply ownership filters before retrieval and delete vectors with their source.
- **Alternatives considered:** Vector columns on Discovery; managed vector database; opaque JSON arrays.
- **Consequences:** One privacy/security boundary and transactional lifecycle. Vector indexes consume space and must be chosen from measured corpus/query behavior. No pgvector dependency or schema is added now.
- **Status:** Revisitable at AI feature design, with PostgreSQL-native storage preferred.

## ADR-013 — Graph storage

- **Context:** Discovery connections and Memory Threads form graph-like relationships.
- **Decision:** Use ordinary PostgreSQL edge and membership tables. Do not add a graph database without measured traversal requirements that PostgreSQL cannot meet acceptably.
- **Alternatives considered:** Dedicated graph database; JSON adjacency lists; recursive CTEs and relational edges.
- **Consequences:** Fewer operational systems and strong ownership constraints. Very deep graph traversal may later require reevaluation.
- **Status:** Final until demonstrated need.

## ADR-014 — PostgreSQL indexing

- **Context:** Primary queries are tenant-scoped library pages, duplicate checks, organization filters, and later search.
- **Decision:** Index foreign keys used for lookup/cascade. Lead private-resource indexes with `user_id`; use stable keyset ordering such as `(user_id, archived_at, created_at DESC, id DESC)`. Use partial indexes for queue states and specialized views only when predicates match real queries. Add GIN full-text and pgvector indexes with their features. Review every index against `EXPLAIN (ANALYZE, BUFFERS)` at representative size.
- **Alternatives considered:** Index every column; rely only on single-column indexes; premature partitioning.
- **Consequences:** Efficient expected queries without speculative write/storage overhead. Query design and index migrations remain coupled.
- **Status:** Final policy; individual indexes revisitable.

## ADR-015 — Time and timezone

- **Context:** Users and sources span time zones, and audit/security ordering must be unambiguous.
- **Decision:** Store instants as PostgreSQL `timestamptz`, write and operate in UTC, and convert at presentation boundaries. Use database or consistently configured application timestamps per transaction. Source publication times may be null when unknown; preserve source timezone/precision separately only if display fidelity later needs it. Use `date` for calendar dates with no instant semantics.
- **Alternatives considered:** Naive timestamps; storing local time plus zone on every row; epoch integers.
- **Consequences:** Unambiguous comparisons and expiry behavior; UI needs a user/browser timezone policy.
- **Status:** Final; display timezone preference is unresolved product input.

## ADR-016 — JSONB policy

- **Context:** Provider payloads and future algorithm output vary, but schemaless storage can hide contracts and sensitive data.
- **Decision:** Use typed columns for identity, ownership, user-visible data, query predicates, and lifecycle fields. JSONB is allowed only for bounded, validated, non-secret auxiliary metadata with a documented schema/version and retention rule. Do not store raw provider responses by default and do not use JSONB as a substitute for relationships.
- **Alternatives considered:** JSONB-first records; separate document database; fully normalized provider-specific tables.
- **Consequences:** Safer validation and indexing; adding a stable new attribute usually requires a migration.
- **Status:** Final policy.

## ADR-017 — Audit boundaries

- **Context:** Security accountability is necessary, but audit logs can become a second copy of private data.
- **Decision:** Audit authentication lifecycle, credential/security changes, account deletion, administrative access, and security-control changes. Consider Discovery deletion/export events when those operations exist. Record actor, safe subject identifier, action, outcome, request ID, and time—not URLs, titles, notes, credentials, tokens, cookies, or fetched/generated content. Restrict audit access and make application writes append-only.
- **Alternatives considered:** Audit every CRUD action with payloads; application logs only; no audit trail.
- **Consequences:** Useful incident evidence with reduced privacy exposure, but it cannot reconstruct content changes. Exact security-event table timing should follow an incident-response requirement.
- **Status:** Final boundary; event catalog and retention are revisitable before production.

## ADR-018 — Retention and deletion

- **Context:** Sessions, visits, jobs, audit events, metadata, derived intelligence, and backups have different operational and privacy needs.
- **Decision:** Define a retention schedule before each data class ships. Revoke sessions immediately on logout/account action; routinely purge expired/revoked sessions and completed jobs; cascade live product and derived data on Discovery/account purge; keep security audits only for a justified fixed period with anonymization where possible; let encrypted backups age out on a disclosed schedule. Legal holds are exceptional, access-controlled, and documented. Never retain private data “just in case.”
- **Alternatives considered:** One retention duration for all tables; indefinite retention; immediate deletion from every backup.
- **Consequences:** More cleanup operations and documented policy work, but lower privacy exposure and clearer user expectations.
- **Status:** Final principle; exact durations require product/legal/operations input before production.
